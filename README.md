# SentinelShop

A small shop (web page, REST API, order worker) wrapped in a secure delivery pipeline, observability, automatic attack response, Kubernetes, Terraform and Ansible. Everything runs locally, with no cloud.

## Quick start

Needs: Docker Engine with Compose v2, make, git, openssl. Optional: pre-commit.

    git clone <repo> sentinelshop && cd sentinelshop
    make up && make smoke

- `make up` creates `.env` with generated secrets if it is missing, then builds and starts the stack.
- The shop is on http://localhost:8080. If that port is busy, set `EDGE_PORT=8088` in `.env` and run `make up` again.
- After you change passwords in `.env`, run `make clean` first. Postgres only reads its password when the volume is created.
- `make clean` removes all containers and volumes. `make down` keeps the data.
- On a fresh clone, run `pre-commit install` to enable the secret-scanning hook.

### If the edge port is busy

`make up` fails with "port is already allocated" or "address already in use" when another program holds the edge port.

1. See what holds it: `ss -ltnp | grep ':8080'`
2. Either stop that program, or choose another port. Set `EDGE_PORT=8088` in `.env` (any free port above 1024), then run `make up && make smoke`. The smoke test reads the port from `.env`, so nothing else changes.
3. The shop only listens on 127.0.0.1, so it is not reachable from other machines.

## Task 1: the app and its containers

- `catalog-api` (FastAPI) serves products, login and orders, and puts each new order on a Redis queue. `order-worker` (two replicas) takes orders off the queue and marks them completed in Postgres. `web` is a static page and `edge` (nginx) sits in front of both.
- Every container runs as a non-root user with a read-only filesystem, all Linux capabilities dropped, and memory and CPU limits. Postgres is the one exception, because it needs to write to its data directory and start as a privileged user.
- Configuration comes only from environment variables (`.env`, generated by `make up`). Logs are JSON and carry a trace id, so one request can be followed across services.
- The stack is split into three compose files: the app (`docker-compose.yml`), monitoring and detection. `make down` and `make clean` stop all three.
- Fault flags for the chaos drill are read only from `chaos/active.env`, and all of them are off when the stack is at rest.

## Task 2: delivery pipeline

- The `Jenkinsfile` has no logic of its own. Every stage calls a make target, so CI and a laptop run the same commands.
- Stages: info, secrets (gitleaks), parallel static checks (Dockerfile lint, SAST with semgrep, config scan with Trivy, Helm lint, Kubernetes scan), build, image scan, push, gitops.
- A failing static check marks that stage and the build red but lets the run carry on, so one run reports every problem. The build stage stops the run immediately if it fails.
- Images are tagged with the short git SHA and pushed to the local registry on `localhost:5000`, but only when the whole run is green.
- The last stage writes the new tag into `values-prod.yaml` in a separate gitops repo (`GITOPS_DIR`) and commits it. The pipeline never runs `kubectl`. Deployment is a separate, manual `make deploy STAGE=prod`.
- It skips branches starting with `demo/`, so the demo branches can never publish a tag.
- A pre-commit hook runs gitleaks and blocks a commit that contains a secret. `make secrets` scans the history of the current branch.
- The branch `demo/insecure` carries three planted fake flaws and is never merged. Its pipeline run must fail.
- One accepted finding: the Ansible test container runs as root on purpose (systemd needs it). It is listed in `.trivyignore.yaml` with the reason.
- Jenkins runs in Docker on port 8081. `make ci` runs the same checks locally.

## Task 3: Kubernetes

- A k3d cluster `shop` (one server, two agents) with a local registry and Traefik as ingress, reachable on port 8088.
- `make k3d-up`, `make k3d-secret`, `make deploy` and `make k3d-smoke` create the cluster, create the secret, install the Helm chart and test it.
- The chart in `helm/shop/` runs Postgres and Redis as StatefulSets and the API, worker and web as deployments, with a disruption budget and topology spread. The worker count is set by an autoscaler.
- Secrets are created by make, not stored in the chart. A config checksum on the pods rolls them when configuration changes.
- A seed job loads the products once. Its name contains the hash of the SQL file, so it runs again only when the data changes.
- Network policies start from default-deny for ingress and egress, then allow DNS, ingress to web and API, and each datastore only from the apps that need it. `make netpol-proof` shows the before and after with throwaway pods.
- Compose and the cluster never run at the same time. The make targets check for this.
- `STAGE=dev` or `STAGE=prod` picks the values file. For prod, the image tag comes from the gitops repo.

## Task 4: Terraform and Ansible

Terraform (`terraform/`, modules `cluster` and `platform`):
- The `cluster` module creates a k3d cluster `shop-tf` and its registry (port 5001, so it never clashes with Task 3). With no cloud, it wraps the k3d command in `terraform_data`. Changing the cluster name or the number of agents makes Terraform replace the cluster.
- The `platform` module uses the Kubernetes provider to create the `shop` namespace, a resource quota, default limits and a default-deny network policy.
- State is local and git-ignored. The provider version is pinned and the lock file is committed.
- `make tf-validate` (format check and validate), `tf-plan`, `tf-apply` and `tf-destroy`. Apply, destroy and apply again works from a clean start.

Ansible (`ansible/`, roles `hardening` and `backup`):
- The target is a privileged Ubuntu 24.04 container running systemd, because this VM has no way to run a second machine. Ansible reaches it through `docker exec`, not SSH.
- `hardening`: a `deploy` user in group `ops`, key-only SSH with root and password login refused, a default-deny firewall that only opens the ports listed in a variable, and `/var/log/shop` with one ACL entry giving group `ops` read access.
- `backup`: a nightly `pg_dump` at 02:00 as a systemd timer, with the service restarting on failure and dumps older than seven days deleted.
- Running the playbook a second time reports `changed=0`. `make ansible-idempotence` checks this.
- Limits of the container target: it shares the host kernel, so the firewall only affects the container's own network, there is no real boot or kernel hardening, and the backup was tested against a throwaway database.

## Task 5: observability

- Prometheus (two days of metrics), cAdvisor and node-exporter for container and host metrics, Loki and Alloy for logs, Grafana for dashboards, Alertmanager for alerts.
- Dashboards are code: they are provisioned from `monitoring/grafana/dashboards`, together with the Prometheus and Loki datasources. A Golden Signals dashboard shows latency, traffic, errors and saturation.
- Four alerts in `monitoring/alerts/sentinelshop.yml`: `HighErrorRate` (5xx share per route above 5 percent for 5 minutes), `HighLatency` (p95 per route above one second for 5 minutes), `QueueBacklog` (more than 50 orders waiting for 10 minutes) and `ContainerRestarting`.
- Alertmanager sends alerts to a small webhook receiver that logs them. Each alert has a runbook in `monitoring/runbooks/`.
- `make mon-up` starts the stack and `make normal-load` creates steady traffic so the dashboards have data.

## Task 6: detection and response

The path of one request: the edge writes a JSON access log, Wazuh reads it and applies custom rules, a matching rule runs the responder, the responder adds the client IP to a blocklist file, and the edge reloads and answers 403 to that IP. Everyone else is unaffected.

| Rule | Trigger | MITRE ATT&CK | OWASP Top 10 |
|---|---|---|---|
| shop-bruteforce-login | 10 failed logins in 60 seconds from one address | T1110 | A07 |
| shop-sqli-probe | SQL injection patterns in the URL | T1190 | A03 |
| shop-xss-probe | script injection patterns in the URL | T1190 | A03 |
| shop-path-traversal | `../` and `/etc/passwd` patterns | T1190 | A01 |
| shop-scan-404 | 15 not-found responses in 30 seconds | T1595.003 | A05 |

- Rules are in `detection/wazuh/local_rules.xml`. The responder (`detection/responder/`) skips allowlisted addresses, ignores repeat alerts, and expires blocks after a set time (10 minutes by default).
- Every decision goes to an audit log and a case file. Each rule has a playbook in `monitoring/playbooks/`.
- False-positive proof: steady normal load (more than 20 requests per second for 5 minutes) produced zero detections. See `evidence/detection/`.
- `make det-up` starts the pieces, `make attack ATTACK=bruteforce` (or `sqli`, `xss`, `traversal`, `scan404`, `all`) runs an attack, and `make det-evidence` produces the proof.
- Run `make det-evidence` on its own, never straight after `make attack`. It takes about 5 minutes and recreates the responder with a 30-second block time so each attack can be shown separately. A block left over from an earlier attack makes every row read `alerts +0`. It also overwrites `evidence/detection/`; pass a folder (`bash scripts/detection-evidence.sh /tmp/test`) to keep the committed evidence.
- The responder keeps its audit log in memory (tmpfs). It is lost when the container is recreated, so the script copies it out.
- Response is reactive: the first few requests of an attack get through before the block lands, a couple of seconds later.

## Task 7: chaos drill and RCA

- `make chaos` picks one hidden fault at random (extra latency, error rate, slow database writes or a memory leak), writes it to `chaos/active.env`, restarts the services and starts load. `make chaos-revert` restores the file.
- Nothing in the logs mentions the fault, so it has to be found from metrics, logs and traces.
- The drill was run blind. The fault was found from Grafana, Loki and a trace, and reverted. The write-up is in `docs/RCA.md`, with screenshots and the timeline in `evidence/chaos/`.
- Lesson recorded in the RCA: `QueueBacklog` is a symptom alert and fires late. The proposed prevention is an alert on worker processing time.

## Decisions

- Everything runs through `make`. The pipeline calls the same targets as a laptop, so a green local run predicts a green CI run.
- Containers are hardened by default. Each exception (Postgres, the Jenkins and Alloy Docker socket mounts, the Ansible test container, the Wazuh manager) is listed under limits.
- The pipeline never deploys. It only writes the new image tag into a separate gitops repo, and deployment is a manual `make deploy STAGE=prod`.
- Wazuh runs as a manager only, with no indexer or dashboard. Rules read the edge access log directly, which keeps the stack small.
- Blocking is done at the edge with `deny` lines in a blocklist file that the responder writes and nginx reloads. Blocks expire by themselves.
- Terraform wraps k3d because there is no cloud. State is local.
- The Ansible target is a systemd container reached through `docker exec`, because there is no second machine.
- The compose project name is fixed to `sentinelshop`, so volumes are shared between any copies of the repo on one machine.

## Known limits

- Redis has no password and environment variables are visible through `docker inspect`. Both are acceptable only on a local network.
- A worker killed with SIGKILL or out of memory loses the one order it was processing. A normal stop (SIGTERM) finishes it.
- The login check has a small timing difference between unknown users and wrong passwords.
- Postgres is not read-only and keeps some capabilities, because it needs them to start.
- Jenkins and Alloy mount the Docker socket, which gives them control of the host's Docker.
- Trivy cannot scan compose files, so the compose files are covered by review and the smoke test only.
- The Wazuh manager runs as root without a read-only filesystem and logs harmless indexer connection retries. Its repeat-alert suppression is per rule, not per source address.
- The responder's API is unauthenticated, reachable only inside the shop network. Its audit log is in memory.
- Prometheus keeps two days of metrics and Loki has no retention limit.
- `HighLatency` is loaded and validated but has not been fired in a test.
- `make secrets` scans the history of the current branch only. The branch `demo/insecure` holds its planted fake secret on purpose.
- The Jenkinsfile points `GITOPS_DIR` at a path on this machine. The gitops repo is a second git repo, and `gitops/` here is a snapshot of it.
- The container-based Ansible target has the limits listed under Task 4.

## What was cut and why

The cuts follow the spec's cut order. Time went to the Must items and to the proof for each of them.

| Cut | Task | What would replace the gap |
|---|---|---|
| SBOM (Syft) and image signing (cosign) | 2, Could | Syft in the pipeline writes an SBOM per image, cosign signs with a local key, and the deploy step verifies the signature |
| SOPS and age encrypted secrets | 3, Could | secrets are generated by make into a Kubernetes secret and never stored in git |
| tflint or checkov in the pipeline | 4, Should | `terraform fmt -check` and `validate` run in `make tf-validate`, and the Trivy config scan already covers the `terraform/` folder |
| Remote Terraform state | 4 | state is local and git-ignored, which is fine for one person |
| Traces in Tempo | 5, bonus | a request is followed across services by the trace id in every JSON log line, searched in Loki |

Done and not cut: graceful degradation when Redis is down (the API returns 503 and stays up), alert routing to a webhook, and responder enrichment.
